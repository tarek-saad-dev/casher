# Membership POS settlement: preparatory plan, not connected to sales

The current POST /api/sales computes totals from browser line prices and optional header discounts before either create transaction. It requires positive payment allocations, so a zero-total membership-only invoice is not yet supported. Both createSale and createSaleLegacyFromRoute must be handled; audited edit/delete uses the extracted/legacy paths and has beforeCommit hooks. The existing synthetic receipt ledger is not an invoice-bound accounting ledger.

This PR adds a pure single-target-line settlement preview reconciled with computeInvoiceItemsTotals. It requires server-resolved catalog prices and approved rules/usage inputs; it rejects stacked discounts across the invoice, repeated target service, exceeded use limit, unsafe legacy decimal range, and any mismatch of payment totals in integer minor units. Free service is supported in mixed paid invoice preview only. Bonus coin settlement and zero-total invoices deliberately fail closed. These conservative pilot decisions are provisional, not approved commercial policy.

Before actual activation: design a separate durable invoice identity and line ledger; resolve tenant/branch/shift and price in the existing sale transaction, revalidate membership/approval/usage there, use a consistent lock order in both creation paths, handle void/reversal and reject unsupported edits, reconcile loyalty/commission/tax/stock and zero-total invoices, prove rollback and retry in isolated SQL and full POS e2e. Do not use a preview as a discount authorization. No endpoint or live sale path is changed by this commit.
